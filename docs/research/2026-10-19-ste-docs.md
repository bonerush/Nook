- 调研日期：2026-10-19

  - **二手/实践**：Write the Docs、阮一峰《中文技术文档的写作规范》、《中文文案排版指北》。

## 〇、先记结论（TL;DR）

1. ASD-STE100 Issue 9 于 **2025-01-15** 发布，由「specification」升级为「standard」，副标题为 *Standard for Technical Documentation*。
2. 结构 = **53 条 writing rules / 9 个 section** + 受控词典（约 **900** 个批准词，约 **1200** 个未批准词及替代词）。下一版 Issue 10 计划 2028 年 1 月。
3. 硬数字只有三条，可直接当 lint 阈值：**操作句 ≤ 20 词**（Rule 5.1）、**说明句 ≤ 25 词**（Rule 6.3）、**段落 ≤ 6 句**（Rule 6.6）；另有**多词名词 ≤ 3 词**（Rule 2.1）。
4. STE **不规定排版**（原文：*STE does not give rules for formatting*）；它管的是语法、词义、句长、结构。警告/注意只规定"先命令后原因"的内容写法。
5. 合规**没有认证机构**：ASD 明确不背书任何声称 "fully compliant" 的工具或公司；合规靠逐条规则评审，工具可选。
6. 中文文档不能照搬 STE 词表，但可以照搬它的**约束类型**：短句、单指令、主动、术语一致、名词链短、段落单主题。
7. 文档结构用 **Diátaxis** 四象限（tutorial / how-to / reference / explanation）分区，README 只留"最短路径"。
8. 一小时内读懂项目 = 一条**有预算的阅读路径**（分钟数 + 每步产出），不是一份"大而全的文档"。

## ① STE 规则清单（可逐条检查）

### 1.1 标准的两大部分

| 部分 | 内容 | 规模 |
|---|---|---|
| Part 1 | Writing rules（写作规则） | 53 条，9 个 section |
| Part 2 | Dictionary（受控词典） | 约 900 批准词；约 1200 未批准词 + 替代建议 |

- 每个批准词只有**一个词义、一个词性**（例：`check` 只批准作名词，如 `do a check`，不作动词）。
- 同义词只保留一个（例：只用 `start`，不用 `begin / commence / initiate / originate`）。
- 拼写基准：美式英语 + Merriam-Webster。
- 未被词典批准的词，只能作为 **technical noun**（技术名词）或 **technical verb**（技术动词）出现；这两类由企业/行业/学科术语库定义。
- **检查动作**：任意一句里出现的实词，要么在批准词表，要么在项目术语表（technical noun/verb），否则打回。

### 1.2 Section 1 — Words（14 条：1.1–1.14）

| 规则 | 要求 | 检查方法 |
|---|---|---|
| 1.1 | 只能用：批准词 / 技术名词 / 技术动词 | 逐词比对词表 + 术语表 |
| 1.2 | 批准词只能按词典标注的词性使用 | 查词性；名词当动词用即违规 |
| 1.3 | 批准词只能用其批准词义 | 查词典释义，不看"常见含义" |
| 1.4 | 只用批准的动词、形容词形式 | 查词典列出的 forms |
| 1.5–1.8 | 技术名词须属可定义类目，且经公司/行业/学科批准 | 术语表有登记 |
| 1.6 | 未批准词只能出现在技术名词内部 | 单独作谓语/修饰即违规 |
| 1.7 | 技术名词不得当动词用 | 例：`*to maintenance the unit` 违规 |
| 1.9 | 选短、易懂的技术名词 | 名词长度与可读性 |
| 1.10 | 不用地区性、俚语、行话 | 术语评审 |
| 1.11 | 同一物件不得用多个技术名词 | 全文同一性检查（同义异名 = 违规） |
| 1.12–1.13 | 技术动词同理，且技术动词不得当名词 | 词性检查 |
| 1.14 | 美式拼写（除非官方另有规定） | 拼写检查 |

> 注：Issue 9 用 **technical noun / technical verb** 全面取代旧称 **technical name**。

### 1.3 Section 2 — Multi-word nouns（2 条）

| 规则 | 要求 | 检查方法 |
|---|---|---|
| 2.1 | 多词名词 **≤ 3 个词** | 数连续名词/形容词修饰串 |
| 2.2 | 超过 3 词须写全 + 用短形式或连字符拆分 | 出现 4 词以上名词串即违规 |

示例（原文）：`Runway light connection resistance calibration`（5 词）→ `Calibration of the resistance of the runway light connection`。

### 1.4 Section 3 — Verbs（7 条：3.1–3.7）

| 规则 | 要求 | 检查方法 |
|---|---|---|
| 3.1 | 只用词典给出的动词形式 | 查 forms 列表 |
| 3.2 | 只允许：不定式 / 祈使式 / 一般现在 / 一般过去 / 一般将来 / 过去分词作形容词 | 出现完成时、进行时即违规 |
| 3.3 | 过去分词只作形容词 | `the adjusted linkage` ✓ |
| 3.4 | 不用助动词构造复杂谓语 | 查 `have/has/had been`、`will be being` 等 |
| 3.5 | **-ing 形式只可作技术名词或技术名词中的修饰语** | 句中出现 -ing 且非名词用法即违规 |
| 3.6 | **用主动语态**；说明文仅在"施动者未知"时可用被动 | 找 `be + 过去分词`；操作文出现被动即违规 |
| 3.7 | 用批准的**动词**描述动作，不用名词化结构 | 禁 `perform an adjustment` → 用 `adjust` |

- 3.5 官方解释（FAQ）：-ing 词可充当多种词性，容易造成歧义与长句，故一般不批准；词典中确实存在 -ing 结尾的**名词/形容词/代词/介词**（`opening` (n)、`remaining` (adj)、`something` (pron)、`during` (prep)）。
- 3.6 官方解释：操作文必须用祈使式，`The component must be installed.` 不是给读者的直接指令，属违规；被动只在施动者未知时允许（`During the transmission, the data was corrupted.`）。

### 1.5 Section 4 — Sentences（5 条）

| 规则 | 要求 | 检查方法 |
|---|---|---|
| 4.1 | 句子短且结构清楚；说明文一句只讲一个主题 | 一句多主题即拆 |
| 4.2 | 不省略词、不用缩写（contractions） | 查 `don't / it's / can't` |
| 4.3 | 复杂内容用**竖排列表**（vertical list） | 逗号串联三个以上动作 → 改列表 |
| 4.4 | 用连接词连接相关句子 | 检查段落内逻辑连接 |
| 4.5 | 名词前按需加冠词或指示形容词（the/a/an、this/these） | 缺冠词、指代不明即违规 |

> 4.5 在 Issue 9 中**从旧版 2.3 移入** Section 4，这是 Issue 9 的结构变化之一。

### 1.6 Section 5 — Procedural writing（5 条，操作文的核心）

| 规则 | 要求 | 检查方法 |
|---|---|---|
| **5.1** | **每句最多 20 个词**；WARNING / CAUTION 也受此限 | 逐句数词 |
| 5.2 | **一句只写一个指令**（除非多个动作同时发生） | 一句出现两个动词短语 → 拆步骤 |
| **5.3** | **指令用祈使式** | 句首应为动词原形 |
| 5.4 | 条件必须先说：条件句在前，用逗号与命令分开 | 条件后置即违规 |
| 5.5 | NOTE 只给信息，不给指令 | NOTE 里出现命令式动词即违规 |

补充原文事实：
- 长句拆成两句时必须确认"两个动作是否同时发生"；同时发生则不能拆成两个 work step。
- **NOTE 不受 5.1 约束**，但 NOTE 中的句子上限是 **25 词**。

示例（原文，20 词上限的边界）：`CAUTION: WHEN YOU REMOVE THE SHROUD (26), BE CAREFUL NOT TO CAUSE DAMAGE TO THE SURFACE OF THE FLANGE ASSEMBLY (22).`（20 词）

### 1.7 Section 6 — Descriptive writing（6 条）

| 规则 | 要求 | 检查方法 |
|---|---|---|
| 6.1 | 信息循序渐进，一句一个 subject | 一句多主语即拆 |
| 6.2 | 用关键词/关键短语建立逻辑结构 | 标题与主题词一致性 |
| **6.3** | **每句最多 25 个词** | 逐句数词 |
| 6.4 | 用段落组织相关信息 | 段落边界是否对应主题切换 |
| 6.5 | **一段只讲一个主题** | 段落主题句检查 |
| **6.6** | **一段不超过 6 句** | 数句号 |

### 1.8 Section 7 — Safety instructions（3 条）

| 规则 | 要求 | 检查方法 |
|---|---|---|
| 7.1 | 用合适的词标明风险等级 | WARNING / CAUTION 是否用对 |
| 7.2 | 以清晰准确的**命令或条件**开头 | 开头是抽象陈述即违规 |
| 7.3 | 给出解释，说明风险或可能的后果 | 缺后果说明即违规 |

原文定义（航空/防务口径）：
- **WARNING**：有**人身伤害或死亡**风险。
- **CAUTION**：有**物体损坏**风险。
- 两种风险同时存在 → 用 WARNING。
- 其他行业可用 `danger / attention / notice` 或图形符号，但内容必须遵守 7.1–7.3；相关标准：ISO 45001:2018、ANSI Z535 系列、ISO 3864。
- **STE 不给排版规则**（原文：*STE does not give rules for formatting*）；示例全大写只是示例，格式由出版物规范/样式指南决定。

反例（原文）：`CAUTION: EXTREME CLEANLINESS OF OXYGEN TUBES IS IMPERATIVE.` 是抽象陈述、且风险等级判错 → 应写成 WARNING + 具体命令 + 后果（爆炸/伤亡）。

### 1.9 Section 8 — Punctuation and word count（7 条）

| 规则 | 要求 | 检查方法 |
|---|---|---|
| 8.1 | 可用标准英文标点，**但不可用分号 `;`** | 搜 `;` |
| 8.2 | 用连字符连接直接相关的词 | 复合修饰语检查 |
| 8.3 | 括号的 7 种允许用途（引用图号、标识件号、标识步骤、缩写、单复数、解释、备选） | 括号是否属这 7 类 |
| 8.4 | 竖排列表中**冒号等同句号**：冒号前 ≤20 词（操作）/ ≤25 词（说明）；列表每项各自重新计数 | 数冒号前词数 |
| 8.5 | 括号内文字**整段算 1 个词** | 计数规则 |
| 8.6 | 数字、数字+单位、缩写、字母数字标识、引文、标题/标牌/标签、机构专有名词，各算 **1 个词** | 计数规则 |
| 8.7 | 连字符连接的词算 **1 个词** | 计数规则 |

> 8.4–8.7 是"怎么数词"的规则。没有这套计数口径，20/25 词的阈值无法执行 —— 这是中文团队最容易漏掉的一环。

### 1.10 Section 9 — Writing practices（4 条 + 8 条一般建议）

| 规则 | 要求 |
|---|---|
| 9.1 | 逐词替换不成立时，改**句子结构**（不能硬换同义词） |
| 9.2 | 每个批准词都用对 |
| 9.3 | 两个词连用不得构成 phrasal verb（短语动词） |
| 9.4 | 术语与措辞**始终一致**（consistent style） |

一般建议 GR-1 ~ GR-8：`that` 连词用法、`with` 介词、代词、`this` 指代、false friends、拉丁缩写、**inclusive language（Issue 9 新增）**、**possessive form（Issue 9 新增）**。

### 1.11 合规判定怎么做（重要）

| 问题 | 官方答案（已核对） |
|---|---|
| 谁认证？ | **没有认证机构**。ASD 与 STEMG 明确**不背书、不认证**任何出售"fully compliant"工具的机构，这些机构也无权使用 ASD/ASD-STE100 商标。 |
| 检查工具必需吗？ | **不必需**，工具可选；"no tool can replace the standard itself"。 |
| 怎么判合规？ | 以 **53 条规则 + 词典 + 技术名词/动词术语表** 逐条评审；标准正文自身也只声称 "comply as much as possible with STE"。 |
| AI 生成文本能默认合规吗？ | 不能。STEMG 白皮书原文：*AI-generated text can appear clear, authoritative, and consistent with STE, even when it does not correctly apply the rules*；*Plausibility must not be confused with verified compliance*。 |
| 版本节奏 | 通常 3 年一版；Issue 9 = 2025-01，Issue 10 计划 2028-01。改动建议用官方 Change Form 提交。 |

**可落地做法（本项目建议）**：把 53 条压成一张 **PR 检查表**（每段 ≤6 句、每句 ≤25 字、操作句 ≤20 字、一句一指令、祈使句开头、无分号、名词链 ≤3、术语在表内），用它代替"感觉像 STE"。

## ② 中文写作等价规则

STE 的约束**不依赖英语**。中文可以逐条对齐它的"约束类型"，但阈值要按汉字重算。

### 2.1 规则映射表

| STE 规则 | 中文等价规则 | 可检查阈值（本项目建议） |
|---|---|---|
| 5.1 操作句 ≤20 词 | 操作步骤一句只做一个动作 | **≤20 个汉字**；超过 30 必拆 |
| 6.3 说明句 ≤25 词 | 说明文字一句只讲一件事 | **≤25 个汉字**（硬上限 30） |
| 6.6 段落 ≤6 句 | 一段一个主题 | **≤6 句**，且首句为主题句 |
| 6.5 一段一主题 | 主题变化必须换段 | 段落内出现"另外/此外"→ 审视是否换段 |
| 5.2 一句一指令 | 一句只出现一个动词性指令 | 一句话两个"然后/再/并"→ 拆 |
| 5.3 祈使句 | 步骤以动词开头 | 步骤首字不是动词 → 改写（"进行/完成/实现"多为坏信号） |
| 3.6 主动语态 | 少用"被/由……所" | 出现"被"字句 → 改主动（施动者未知除外） |
| 3.7 动词描述动作 | 不用"名词化 + 虚动词" | 禁"进行/予以/加以/作出 + 名词"（进行优化 → 优化） |
| 3.5 禁 -ing | 禁"……的……的……"长定语与"……时/……过程中"套叠 | 定语链 ≤2 层；一个"的"以上要审 |
| 2.1 名词 ≤3 词 | 名词链 ≤3 个名词 | "XX 模块 YY 服务 ZZ 配置项" → 加"的"或拆句 |
| 1.11 一物一名 | 同一概念全文一种写法 | 术语表唯一来源；同义异名 = 缺陷 |
| 4.2 不用缩写 | 中文不适用缩写规则，但**不省主语、不省谓语** | 避免"已修复"这类无主语残句（在说明文中） |
| 4.5 冠词 | 中文无冠词，等价要求是**指代明确** | 每处"其/该/此/它"必须能唯一回指 |
| 8.1 无分号 | 中文同样避免用分号串长句 | 一段内分号 >0 即审 |
| 9.3 无短语动词 | 避免"对……进行……"、"就……而言"等框架 | 见禁用词清单 |
| 7.x 安全写法 | 危险提示 = 命令/条件 + 后果 | 缺"否则会……"即不合规 |

补充（阮一峰《中文技术文档的写作规范》）：
- **句长分档**：≤20 字最佳；20–29 字可接受；30–39 字需语义明确；**>40 字一律不可接受**（原文 30–39 段有笔误，评论区已指出）。
- 被动改主动；不用非正式语体；"的/地/得"要用对；代词必须唯一指代；名词前不要堆形式词；**能用肯定句就不用否定句**；避免双重否定。

### 2.2 中文量化标准（可直接写进 lint）

| 指标 | 阈值 | 例外 |
|---|---|---|
| 操作句长 | ≤20 汉字 | 命令 + 条件句合计 ≤25 |
| 说明句长 | ≤25 汉字 | 引用原文不动 |
| 段落句数 | ≤6 | 列表不算句 |
| 段落主题数 | 1 | — |
| 名词链长度 | ≤3 个名词 | 专有名词（如 `NSStatusItem`）整体算 1 个 |
| 术语变体数 | 1（每概念） | 首次出现可给英文原名 |
| 分号数 | 0 | 代码块内不计 |
| 虚动词结构 | 0 | "进行/予以/加以/作出 + 名词" |
| 双重否定 | 0 | — |
| 每节术语表覆盖 | 100% | 未登记术语不得使用 |

### 2.3 术语表模板（术语一致性的唯一来源）

| 中文（唯一写法） | 英文/代码标识 | 定义（一句话） | 禁用变体 |
|---|---|---|---|
| 提词窗 | teleprompter window / `TeleprompterWindow` | 显示讲稿的浮动窗口 | 提词器窗口、字幕窗 |
| 断句 | segmentation | 把讲稿切成朗读单元 | 分词、切分 |
| 讲稿 | script | 用户输入的文本 | 稿件、文本 |

**检查动作**：CI 里对 `禁用变体` 列做全文 grep，命中即失败。

## ③ 文档目录结构提案（面向"一小时读懂"）

### 3.1 Diátaxis 四象限（官方定义，已核对）

| 类型 | 回答的问题 | 面向 | 形态 | 本项目对应 |
|---|---|---|---|---|
| Tutorial（教程） | "Can you teach me to…?" | 学习 | 一课，手把手 | `docs/tutorials/` 15 分钟做出第一次提词 |
| How-to（操作指南） | "How do I…?" | 工作/目标 | 一串步骤 | `docs/how-to/` 换模型、调配色、打包安装 |
| Reference（参考） | "What is…?" | 工作/信息 | 干燥的事实 | `docs/reference/` 快捷键、配置项、文件布局 |
| Explanation（解释） | "Why…?" | 学习/理解 | 论述 | `docs/explanation/` 为什么用 Keychain、为什么不用 SwiftPM |

Diátaxis 官方警告：**四类边界模糊是文档问题的最大来源**（"Crossing or blurring the boundaries … is at the heart of a vast number of problems"）。所以：教程里不要塞参考表，参考里不要写教程。

### 3.2 目录树提案

```text
README.md                      # ≤1 屏：它是什么 / 为什么有用 / 30 秒跑起来 / 去哪问
docs/
  index.md                     # 文档地图 + 三条阅读路径（新手/贡献者/排障）
  tutorial/
    01-first-run.md            # 15 分钟：装好并提一次词
  how-to/
    change-model.md
    build-and-install.md
    troubleshoot-ai.md
  reference/
    shortcuts.md               # 快捷键（唯一来源）
    settings.md                # 配置项与默认值
    file-layout.md             # 目录与构建产物
  explanation/
    architecture.md            # 模块图 + 数据流
    why-keychain.md
    why-no-swiftpm.md
  adr/                         # 架构决策记录（只增不改）
    0001-keychain.md
  glossary.md                  # 术语表（②2.3 模板）
  style-guide.md               # 本文件 ①②④ 的落地版
```

### 3.3 60 分钟阅读路径（给"新手第一小时"）

| 分钟 | 读什么 | 产出（可验收） |
|---|---|---|
| 0–5 | `README.md` | 能用自己的话说出"这个软件解决什么问题" |
| 5–20 | `tutorial/01-first-run.md` | 本机成功提词一次 |
| 20–30 | `explanation/architecture.md`（只看图 + 图注） | 能画出 3 个模块与数据流 |
| 30–40 | `reference/file-layout.md` | 能说出改某个功能该动哪个目录 |
| 40–50 | `adr/0001` + `glossary.md` | 能解释 1 个"为什么这样设计" |
| 50–60 | `how-to/build-and-install.md` | 本地构建成功一次 |

**路径设计原则**（本项目建议）：
1. 每步都有**可验收产出**，没有产出的章节不进第一小时。
2. 先"能跑"，再"能改"，最后"能解释"——对应 Diátaxis 的 learning → goal → information → explanation 循环（官方 map 页原文描述了这个顺序）。
3. 第一小时**不要求**读 reference 全表；reference 是查阅用的，不是通读用的。

### 3.4 README 反模式清单（逐条可查）

| 反模式 | 为什么坏 | 修法 |
|---|---|---|
| 只有徽章和一句 slogan | 读者拿不到"最短成功路径" | 首屏给"30 秒跑起来"命令 |
| 把 FAQ 当文档 | Write the Docs 指出：很快过期、内容发散、难检索、往往不是真的高频问题 | 拆进 how-to / reference |
| 用 README 装下全部文档 | GitHub 官方：README 只应包含"上手与贡献"必需信息；超过 500 KiB 会被截断 | 长文移入 `docs/` |
| 安装步骤 20 行 | 官方建议：基础安装压到几行，细节外链 | 首屏 3 行 + 链接 |
| 只写"是什么"不写"为什么有用" | 读者不知道是否与自己相关 | 加"适用场景/不适用场景" |
| 无版本、无许可证、无求助入口 | 无法判断可用性与责任边界 | 三件套补齐 |
| 中英混排无空格、半角标点 | 阅读摩擦 | 见 ④ 排版检查 |
| 截图代替文字步骤 | 不可搜索、不可复制 | 文字为主的步骤 + 可选截图 |

### 4.2 "文字重叠"怎么查（必须看渲染结果）

Mermaid 的布局是自动的，**源码层面无法保证不重叠**。可执行的检查顺序：

1. 固定渲染宽度（例如 GitHub 正文宽度 900 px）下截图；
2. 检查四类重叠：节点文字溢出边框、边标签压线、子图标题压节点、图例压内容；
3. 任一处重叠 → 缩标签 / 拆图 / 改方向 / 减少同层节点；
4. 截图纳入 PR 附件（肉眼可复核，机器难判定）。

> 这四条是工程实践约定（**本项目建议**），不是任何标准原文。

### 4.3 排版检查清单

| 项 | 规则 |
|---|---|
| 标题层级 | 不跳级（h2 → h3，不出现 h2 → h4）；一篇只有一个 h1 |
| 列表 | 并列项用无序；有顺序/有步骤用有序；列表项结尾标点统一 |
| 代码块 | 必须有语言标识；命令与输出分开 |
| 表格 | ≤5 列；单元格不换行超过 2 行；表头必须有意义 |
| 链接 | 用描述性文字，禁"点击这里"（Apple HIG 同款要求） |
| 数字与单位 | 数字与单位之间空格（`20 分钟`、`6 mm`） |
| 中英混排 | 中文与英文/数字之间加空格（《中文文案排版指北》） |
| 标点 | 中文用全角标点；英文整句/专名内用半角 |
| 强调 | 少用加粗；一屏加粗 ≤3 处 |
| 段落 | ≤6 句（与 ② 一致） |
