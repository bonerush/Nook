# Nook 2.0 交付工作流

## 用途

本页记录 Nook 2.0 的工作方式。

它可复用于下一次大改。

## 角色

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| 主代理 | 当前会话 | 设计、实现、集成、修复 |
| 调研代理 | 4 个独立 subagent | 查证 Apple 规范、动效、架构、STE |
| 审查代理 | 3 个独立 subagent | 代码、界面、文档 |
| 用户 | 项目所有者 | 提出目标，验收结果 |

主代理默认负责实现。

审查必须由独立代理完成。

## 七个阶段

### 阶段 0：基线

1. 记录测试数量。
2. 记录截图。
3. 记录用户数据哈希。
4. 确认工作区干净。

产出：基线证据。

### 阶段 1：调研

1. 拆成四个互不依赖的问题。
2. 同时派四个调研代理。
3. 要求每个代理写入独立文件。
4. 主代理只读摘要，不读全文。

产出：docs/research/ 四份报告。

### 阶段 2：设计

1. 合并调研结论。
2. 写目标、原则、架构、界面、文档方案。
3. 写验收标准。
4. 写取舍，不隐藏偏离。

产出：设计文稿。

### 阶段 3：计划

1. 拆成可独立验证的任务。
2. 每个任务写文件、接口、验证命令。
3. 标注检查点。

产出：实施计划。

### 阶段 4：实现

1. 先做结构，再做界面，最后做文档。
2. 每个任务结束运行测试与构建。
3. 每个任务单独提交。
4. 保持零警告。

产出：可运行的提交序列。

### 阶段 5：审查

同时派三个审查代理。

- 代码审查：行为、并发、安全、质量门。
- 界面审查：必须看截图。
- 文档审查：必须做新读者测试。

审查代理只读。它们写报告，不改代码。

产出：三份报告。

### 阶段 6：收敛

1. 按 blocker 优先修复。
2. 修复后重跑全部检查。
3. 让原审查代理复验关键项。
4. 更新文档与记忆。

产出：可发布版本。

### 阶段 7：安装

1. 退出旧版本。
2. 校验 bundle id。
3. 安装到 /Applications。
4. 对比用户数据哈希。
5. 启动并确认。

产出：已安装版本。

## 质量门

| 门 | 命令 | 标准 |
| --- | --- | --- |
| 构建 | ./scripts/build.sh | 成功，零警告 |
| 测试 | ./scripts/test.sh | 全部通过 |
| 文档 | ./scripts/check-docs.py | 至少 80 分 |
| 截图 | 预览参数 | 无裁切，无重叠 |
| 审查 | 三份报告 | 无 blocker |

## 证据

- 测试输出。
- 截图。
- 数据哈希。
- 审查报告。
- git 提交。
